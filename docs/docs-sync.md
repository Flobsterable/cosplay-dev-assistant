# Обновление документации после слияния PR

Цель пользователя: «Приведи документацию в соответствие с изменениями PR».
Пути документов и исходников выбирает агент, указывать отдельные файлы не требуется.
Существующие /help и автоматическое ревью остаются доступными.

## Два сценария работы с файлами

1. Поиск определений и мест использования изменённых API. MCP get_sync_context читает
   обычные файлы из Git-объектов. Агент видит каталог, выбирает read/search и получает
   найденные фрагменты с путями и строками. Изменённые участки кода предварительно
   прочитаны. Markdown не расходует бюджет чтения кода: существующие документы
   передаются отдельным контекстом. Проверяющий агент может запросить дополнительные
   исходники. Фиксированных порогов объёма документов, diff и выбранного кода для /sync нет.
   Ёмкость чтения равна размеру корпуса; защита от зацикливания масштабируется с числом разделов.
2. Обновление README и docs по коду. change_agent сопоставляет diff с прочитанными
   исходниками; docs_sync_agent выбирает существующие документы и предлагает точечные
   замены текста. Программа собирает полные версии локально, проверяя точное уникальное
   совпадение каждого заменяемого фрагмента. Размер ответа не зависит от неизменённого текста.
   Перед выводом/записью независимый docs_verifier повторно ищет подтверждение новых
   утверждений в коде. По умолчанию результат — проверенный unified diff;
   --apply сохраняет изменения только после успешной проверки.

Если документов больше трёх, генерация сразу выполняется по одному файлу.
Для небольшого набора, если общий ответ обрезан лимитом токенов,
генератор повторяет запрос отдельно для каждого существующего документа.
Частичный ответ не используется; каждый предложенный документ проверяется отдельно,
и все проверки должны завершиться до первой записи. Отказ проверяющего по-прежнему останавливает обновление.

Чтение исходников использует тот же фильтр и индекс Git-объектов, что и PR review:
Kotlin, Gradle, TOML, properties, XML, Markdown и workflows. Секреты, скрытые пути,
симлинки и бинарные файлы исключаются. Изменения для /sync ограничены Kotlin/Gradle/release.yml.
Неизвестные пути записи запрещены. При неполном поиске обновление останавливается. Проверки модели не гарантируют смысловую правильность правок.

## Проверка предложения до сохранения

Программа разбирает Markdown-ссылки и изображения, включая reference links, и проверяет
существование относительных целей. Для README/docs проверяются якоря заголовков и явные
HTML id/name. Проверка видит предложенное содержимое до записи и замечает ссылки из
неизменённых документов, сломанные переименованием раздела. Примеры ссылок внутри
блоков кода не проверяются; старые битые ссылки вне изменений не блокируют предложение.
Внешние URL, HTML href и якоря файлов вне прочитанного README/docs не проверяются.

Затем docs_verifier проверяет каждый изменённый документ отдельным запросом:
его оригинал, предложение и собственный patch. Каждый документ получает новый поиск
подтверждений, без накопления исходников предыдущих проверок. Он сам выбирает дополнительные
исходники, проверяет имена классов/API, параметры и примеры команд. Для исторического
диапазона на более новом checkout проверяющий получает текущий код, чтобы не вернуть
устаревший контракт. Для каждого изменённого документа нужен явный результат проверки.
При противоречии, недостающем подтверждении, некорректном ответе модели или исчерпании
поиска запись отменяется. Подтверждённые замечания проверяющего передаются автору
для исправления затронутых документов (до двух попыток), после чего все документы
проверяются заново. При неполном поиске или некорректном ответе запись отменяется
без такого исправления. Ошибка содержит причину.

Это статическая проверка: команды из Markdown, сборка и тесты приложения не исполняются.
Семантическую проверку выполняет модель, поэтому результат всё равно нужно просматривать.
Дополнительный проход выполняет отдельный поиск и проверочный вызов модели на каждый
изменённый документ; стоимость и длительность /sync увеличиваются. Лимиты контекста
и ответа, установленные провайдером модели, сохраняются. Один слишком большой документ
или запрос всё ещё может превысить возможности модели: агент явно сообщает ошибку
и не сохраняет непроверенное предложение. Встроенных порогов 40k/80k для Markdown,
300 документов и 128k/1.5M для исходников в /sync больше нет.

## Ручной запуск

В tools/dev-assistant/.env задайте PROJECT_ROOT, LLM_API_KEY, LLM_MODEL и при необходимости LLM_BASE_URL.

```bash
cd tools/dev-assistant
npm ci
node src/cli.js /sync BASE_SHA --head MERGED_SHA
node src/cli.js /sync BASE_SHA --head MERGED_SHA --apply
```

BASE_SHA — целевая ветка перед слиянием, MERGED_SHA — результат слияния PR.
Без --head используется HEAD. Диапазон содержит только закоммиченные изменения.
Перед сохранением docs должны быть чистыми; изменения файлов или checkout во время
генерации отменяют запись. Новые файлы в этом сценарии не создаются.

## GitHub Actions

Скопируйте examples/workflows/docs-sync.yml в .github/workflows/docs-sync.yml
репозитория приложения. Runtime уже закреплён на коммите ассистента с этой реализацией;
при обновлении агента обновляйте и его ref в workflow. Шаблон не устанавливается в сам репозиторий
ассистента: его документация описывает JavaScript, а целевой сценарий рассчитан на KMP.

Настройте Secret LLM_API_KEY, Variables LLM_MODEL/LLM_BASE_URL и разрешение
Settings → Actions → General → Allow GitHub Actions to create and approve pull requests.

Workflow реагирует на pull_request: closed только при merged=true в main/develop.
Он проверяет SHA и принадлежность диапазона текущей ветке, запускает тот же CLI,
сохраняет отчёт с diff как Actions artifact и создаёт draft PR.
Ветка automation/docs-sync-<MERGED_SHA> постоянна для диапазона, поэтому повтор запуска
обновляет существующее предложение. Ветки самого агента исключены из запуска.
Если docs уже актуальны, PR не создаётся. Автоматического слияния нет.

Fork PR автоматически пропускаются: pull_request не выдаёт им секреты и токен записи.
Для них или для повторной обработки выберите Run workflow на целевой ветке и задайте
полные SHA base/head. Для точного повтора события также можно использовать Re-run jobs.
Вызовы LLM могут давать разные формулировки; воспроизводимы диапазон и процедура,
а не побайтовое совпадение ответа модели.

## Воспроизводимая проверка без API-ключа

```bash
cd tools/dev-assistant
npm ci
node --test --test-name-pattern="sync searches API usages" test/assistant.test.js
npm test
```

Интеграционный сценарий создаёт Git-проект с Main.kt, Screen.kt, README.md и docs/.
Через настоящий MCP агент ищет Festival.city, получает определение и место использования,
сохраняет README и руководство. После коммита документации повтор того же диапазона
возвращает пустой diff. Ответы модели подменены, платные запросы не выполняются.
Другие проверки покрывают предпросмотр, применимость patch, запрет записи поверх
локальных правок и остановку при неполном поиске.
test/documentation.test.js проверяет аудит отсутствующего описания параметра, учёт docs
из самого PR, относительные ссылки и якоря, а также отказ от записи при выдуманном API,
битой ссылке или неполной проверке. Все ответы модели в тестах подменены.
