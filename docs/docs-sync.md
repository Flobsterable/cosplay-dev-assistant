# Обновление документации после слияния PR

Цель пользователя: «Приведи документацию в соответствие с изменениями PR».
Пути документов и исходников выбирает агент, указывать отдельные файлы не требуется.
Существующие /help и автоматическое ревью остаются доступными.

## Два сценария работы с файлами

1. Поиск определений и мест использования изменённых API. MCP get_sync_context читает
   обычные файлы из Git-объектов. Агент видит каталог, выбирает read/search и получает
   найденные фрагменты с путями и строками. Проверяющий агент может запросить дополнительные
   источники. Лимиты: 8 шагов и 60 000 символов выбранного контекста.
2. Обновление README и docs по коду. change_agent сопоставляет diff с прочитанными
   исходниками; docs_sync_agent выбирает существующие документы и предлагает их содержимое.
   По умолчанию результат — применимый unified diff; --apply сохраняет изменения.

Чтение исходников использует тот же фильтр и индекс Git-объектов, что и PR review:
Kotlin, Gradle, TOML, properties, XML, Markdown и workflows. Секреты, скрытые пути,
симлинки и бинарные файлы исключаются. Изменения для /sync ограничены Kotlin/Gradle/release.yml.
Неизвестные пути записи запрещены. При неполном поиске или превышении лимита корпуса
обновление останавливается. Проверки модели не гарантируют смысловую правильность правок.

## Ручной запуск

В tools/dev-assistant/.env задайте PROJECT_ROOT, LLM_API_KEY, LLM_MODEL и при необходимости LLM_BASE_URL.

```bash
cd tools/dev-assistant
npm ci
node src/cli.js /sync BASE_SHA --head MERGED_SHA
node src/cli.js /sync BASE_SHA --head MERGED_SHA --apply
```

BASE_SHA — целевая ветка перед слиянием, MERGED_SHA — результат слияния PR.
Без --head используется HEAD. Диапазон содержит только закоммиченные изменения.
Перед сохранением docs должны быть чистыми; изменения файлов или checkout во время
генерации отменяют запись. Новые файлы в этом сценарии не создаются.

## GitHub Actions

Скопируйте examples/workflows/docs-sync.yml в .github/workflows/docs-sync.yml
репозитория приложения. Замените REPLACE_WITH_DOCS_RUNTIME_SHA на SHA коммита
ассистента, содержащего эту реализацию. Шаблон не устанавливается в сам репозиторий
ассистента: его документация описывает JavaScript, а целевой сценарий рассчитан на KMP.

Настройте Secret LLM_API_KEY, Variables LLM_MODEL/LLM_BASE_URL и разрешение
Settings → Actions → General → Allow GitHub Actions to create and approve pull requests.

Workflow реагирует на pull_request: closed только при merged=true в main/develop.
Он проверяет SHA и принадлежность диапазона текущей ветке, запускает тот же CLI,
сохраняет отчёт с diff как Actions artifact и создаёт draft PR.
Ветка automation/docs-sync-<MERGED_SHA> постоянна для диапазона, поэтому повтор запуска
обновляет существующее предложение. Ветки самого агента исключены из запуска.
Если docs уже актуальны, PR не создаётся. Автоматического слияния нет.

Fork PR автоматически пропускаются: pull_request не выдаёт им секреты и токен записи.
Для них или для повторной обработки выберите Run workflow на целевой ветке и задайте
полные SHA base/head. Для точного повтора события также можно использовать Re-run jobs.
Вызовы LLM могут давать разные формулировки; воспроизводимы диапазон и процедура,
а не побайтовое совпадение ответа модели.

## Воспроизводимая проверка без API-ключа

```bash
cd tools/dev-assistant
npm ci
node --test --test-name-pattern="sync searches API usages" test/assistant.test.js
npm test
```

Интеграционный сценарий создаёт Git-проект с Main.kt, Screen.kt, README.md и docs/.
Через настоящий MCP агент ищет Festival.city, получает определение и место использования,
сохраняет README и руководство. После коммита документации повтор того же диапазона
возвращает пустой diff. Ответы модели подменены, платные запросы не выполняются.
Другие проверки покрывают предпросмотр, применимость patch, запрет записи поверх
локальных правок и остановку при неполном поиске.
