# Автоматическое ревью pull requests

## Что проверяется

Базовый профиль `tools/dev-assistant/profiles/base-review.md` описывает проверки для
проектов Kotlin Multiplatform; Compose/Material 3, Ktor,
корутины, сериализация, даты, Gradle и релизы. Версии берутся из Git-снимка приложения.

Порядок приоритетов: баги и регрессии → архитектурные последствия → полезные рекомендации.
Проверяются состояния UI, эффекты/ключи Compose, отмена корутин, владение HttpClient,
ошибки HTTP/DTO, резервные данные, границы модулей, expect/actual и платформенные интеграции.
Не требуется внедрять ViewModel, DI, Navigation или БД без конкретной необходимости.

Каждое замечание содержит приоритет, изменённую строку, сценарий проявления,
последствие, предлагаемое исправление и ссылки на прочитанные источники.
Категории не заполняются искусственно: если подтверждённых замечаний нет, так и написано.

## Пайплайн

1. GitHub Action срабатывает на opened/synchronize/reopened/ready_for_review PR.
2. Загружается базовая ветка; head PR fetch-ится как Git-объект и не запускается.
3. Анализатор получает список файлов и diff merge-base(base, head)..head.
4. Из Git blobs строится корпус Markdown + Kotlin/Gradle/TOML/properties/XML/workflows.
   Исходники читаются из head, старые версии изменённых файлов — из base.
5. Агент сам выбирает документы, определения, вызывающий код и контракты; доступны
   чтение и BM25-поиск, затем отдельная проверка покрытия каталога.
6. base_reviewer проверяет общие правила агента (B-ID), project_reviewer независимо
   проверяет `docs/review-rules.md` приложения (P-ID). review_verifier проверяет
   оба черновика, убирает ложные замечания и объединяет одинаковые проблемы.
7. docs_auditor отдельно собирает контекст для проверки README/docs по публичным API,
   параметрам, командам и поведению PR. До первого вызова поиска в контекст загружаются
   все доступные README/docs из head и изменённые участки кода из head/base. Поиск
   дополняет их зависимостями; независимая проверка покрытия обязательна. Уже обновлённые документы
учитываются. Уже прочитанные разделы отмечены в каталоге; запрос без новых разделов
переключает сборщик на независимую проверку покрытия, а не означает автоматический
успех. Подтверждённые баги кода передаются аудитору, чтобы не закреплять регрессии
   в документации. Непустой черновик замечаний проверяется повторным независимым вызовом.
8. Код валидирует пути, источники и привязку к действительно изменённым строкам.
9. Для каждого проверенного SHA публикуется отдельный комментарий бота: баги,
   архитектура, рекомендации и актуальность документации. Повторный запуск на том же SHA обновляет только
   его комментарий. Отчёты предыдущих коммитов сохраняются.
   Перед записью проверяется, что head PR ещё тот же. Отчёт сохраняется в артефакт.

Сборка, Gradle и код PR в этом процессе не исполняются. Отдельные compile/test jobs
остаются ответственностью приложения. AI-ревью не выставляет автоматическое approval
и не является гарантией отсутствия багов.

## Два независимых слоя правил

Базовые правила хранятся в runtime агента и не зависят от конкретного приложения.
Особенности продукта задаются в `docs/review-rules.md` целевого репозитория.
Для правила проекта нужен заголовок `## P-ID — название` и описание контракта,
оснований и способа проверки. Новые правила не требуют изменения кода агента.

Проектный профиль берётся строго из target base tip PR. Head-версия правил не
подменяет действующую: изменения правил в PR анализируются как изменения файлов
и вступают в силу после слияния. При отсутствии проектных правил этот проход
явно помечается как не выполненный; базовое ревью продолжает работать.
Правила проекта не могут отключать базовую проверку или задавать команды/вывод.
В JSON каждого замечания есть rules с layer/base|project и реальными ID правил;
Markdown показывает оба итога и происхождение каждого замечания.

## Установка в целевой проект

Шаблон: `examples/workflows/ai-review.yml`. Скопируйте в `.github/workflows/ai-review.yml`
приложения. Runtime уже закреплён по SHA коммита ассистента с аудитом документации,
а не по изменяемой ветке PR. При обновлении агента обновляйте ref в установленном workflow.

В Settings → Secrets and variables → Actions репозитория приложения:

- Secret `LLM_API_KEY` — ключ DeepSeek.
- Variable `LLM_MODEL` — необязательно; по умолчанию `deepseek-flash`.
- Variable `LLM_BASE_URL` — необязательно; по умолчанию `https://api.deepseek.com`.

GITHUB_TOKEN выдаётся GitHub автоматически. Workflow использует contents:read
и pull-requests:write для комментария. Fork PR и draft PR пропускаются;
для внешних PR не используется pull_request_target и не выдаются секреты.
При отсутствии API-ключа job завершается понятной ошибкой, а не фиктивным ревью.

## Локальный запуск

Задайте PROJECT_ROOT и настройки модели в tools/dev-assistant/.env. base/head должны
существовать в целевом Git-репозитории. Запуск не меняет код и документацию приложения.

```bash
cd tools/dev-assistant
npm run review -- --base develop --head feature/example --repo OWNER/REPOSITORY --output /tmp/pr-review
```

Получите review.md и review.json. Без --publish запросов на запись в GitHub нет.
Для публикации нужны --publish --pr NUMBER и GITHUB_TOKEN с правом комментария.
Не вводите токены в аргументы команды.

## Ограничения

Не более 100 изменённых файлов и 80 000 символов diff. Файлы корпуса ограничены
128 КБ каждый, общий корпус — 1,5 МБ. Секретные/скрытые файлы, local.properties,
симлинки и бинарные файлы исключаются. Пропуски перечислены в JSON; при них
Markdown явно сообщает о неполной проверке. Агентный контекст ограничен 100 000
символов и 8 шагами. Большой diff отклоняется целиком, не анализируется молча частично.
Аудит документации использует до 8 шагов поиска и общий бюджет 140 000 символов
прочитанных разделов (прежние 60 000 для поиска + 80 000 для документации).
README/docs ограничены 80 000 символами внутри этого бюджета. Начальные источники
учитываются в общем размере, повторное чтение уже выбранного раздела не расходует
его повторно. Если контекст не поместился или проверка покрытия не завершилась,
JSON содержит статус limit, точную причину, использованные шаги/символы, число
отклонённых запросов и список отложенных разделов с путями/строками. Markdown
показывает «не завершён», причину и до десяти непрочитанных разделов; полный список
остаётся в review.json. Это не вывод «документация актуальна».
CLI сохраняет отчёт и публикует доступные результаты, затем возвращает код 1 при
незавершённом аудите документации. GitHub Actions такой запуск не считает успешным.
Аудит добавляет вызовы модели и расход API.
Два чтения head перед комментарием уменьшают риск устаревшего отчёта, но запись API
не транзакционна с обновлением PR; SHA всегда указан в комментарии.

В артефакт попадают замечания и метаданные источников, а не полные тексты исходников
или запросы к модели. Код/документы считаются данными, их инструкции не выполняются.
JSON содержит documentationAudit с отдельными замечаниями, статусом и метаданными
источников; Markdown использует ссылки D1, D2 и т. д. Эти замечания публикуются в
общем комментарии, а существующие inline-комментарии относятся к ревью кода.

## История отчётов

Новый коммит PR получает отдельный отчёт в комментарии бота. Повторный запуск
на том же SHA обновляет его существующий комментарий. Отчёты предыдущих
коммитов сохраняются, чтобы можно было проследить исправление замечаний.
Markdown- и JSON-отчёты доступны в артефактах соответствующего запуска Actions.

## Замечания в diff

Подтверждённые замечания также публикуются как GitHub Review с событием COMMENT,
привязкой к commit_id, пути, строке и стороне LEFT/RIGHT. Каждое содержит причину,
исправление, правила и ссылку на полный отчёт. Автоматического approval или
request changes нет. Повторный запуск того же SHA обновляет собственные обсуждения,
не создавая дублей; исчезнувшее замечание помечается как не подтверждённое повторной
проверкой. Обсуждения предыдущих коммитов сохраняются.
