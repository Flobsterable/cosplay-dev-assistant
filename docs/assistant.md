# Консольный помощник разработчика

Отдельный сервис в `tools/dev-assistant`, Node.js 22+ (Docker использует Node 24).
Один процесс приложения запускает MCP-сервер дочерним процессом через stdio.
Сабагенты — отдельные вызовы LLM с разными инструкциями и контекстом, а не отдельные VPS.
Код Kotlin-приложения и Gradle-сборка от помощника не зависят.

## Оркестратор и сабагенты

`/help вопрос` использует агентный поиск по README/docs и текущую Git-ветку через MCP.
Сначала retrieval_agent получает каталог всех документов с заголовками, диапазонами строк
и краткими началами разделов. Модель сама выбирает действия read (документ целиком или
разделы), search (BM25 по сформулированному ею запросу) и done. Результаты чтения возвращаются
модели, и она может продолжить поиск. Пустая выдача BM25 не останавливает работу.
Перед ответом coverage_agent сопоставляет вопрос, весь каталог и прочитанные разделы;
он может запросить дополнительные источники. Специальных правил для отдельных тем нет.
Лимиты: 8 шагов выбора/проверки и 100 000 символов прочитанного контекста.
Если лимит достигнут, CLI явно отмечает незавершённую проверку; модель не гарантирует
абсолютную полноту. Чтение ограничено снимком README/docs, произвольные пути запрещены.
Оркестратор через LLM выбирает одного или двух сабагентов и режим parallel/sequential:

- docs_agent отвечает по найденным фрагментам README и docs.
- reviewer_agent сверяет сложный ответ с той же документацией; не читает исходники.
- В parallel поручения выполняются одновременно. В sequential второй получает отчёт первого.
- Оркестратор проверяет названия агентов и собирает ответ с источниками, сохраняя существенные детали.
- Список файлов и содержимое кода для /help не запрашиваются. Названия модулей берутся из документации.
- Git-ветка получается из MCP; решение о достаточности Git-контекста тоже принимает модель.

`/sync <base>` — фиксированная последовательная цепочка:

1. MCP get_project_diff читает закоммиченные изменения от base до HEAD.
2. change_agent выделяет изменения поведения, контрактов и сборки.
3. docs_sync_agent сверяет анализ с diff и предлагает полные версии затронутых документов.
4. Программа проверяет пути и формат, формирует unified diff.
5. По умолчанию CLI показывает предпросмотр; --apply сохраняет файлы.

Список документов определяется в целевом проекте: существующие README.md и docs/**/*.md.
Скрытые пути и симлинки исключаются; новые произвольные пути не принимаются.
Перед записью проверяются незакоммиченные изменения docs и неизменность Git-контекста.
Ассистент не коммитит и не публикует релизы. Смысловую правильность предложений проверяет разработчик.
Если документация уже актуальна или diff не затрагивает поддерживаемые файлы, изменений может не быть.

## RAG и MCP

RAG использует чтение выбранных моделью документов и BM25 для поисковых действий.
Это retrieval-augmented generation без эмбеддингов и векторной базы.
Корпус — только README.md и docs/**/*.md. Скрытые файлы и симлинки пропускаются.
Каждый вопрос перечитывает маленький корпус, поэтому сохранённые изменения сразу участвуют в поиске.
`npm run index` сохраняет диагностический снимок .cache/index.json; ответы используют свежие данные.

MCP реализован официальным @modelcontextprotocol/sdk, а не прямой подстановкой ветки в prompt:
initialize → tools/list (в диагностике/тестах) → tools/call.
Инструменты: get_current_branch и get_project_diff. Последний используется только явной командой /sync.
Инструмента просмотра списка файлов нет.
Diff ограничен *.kt, *.kts, *.toml, gradle.properties и release.yml; лимит 60 000 символов.
Рабочие незакоммиченные изменения кода в /sync не входят. Для них сначала нужен коммит.
Ветка относится к копии репозитория на VPS. Удалённая GitHub-ветка не обновляется автоматически.

## Локальный запуск

```bash
cd tools/dev-assistant
npm ci
cp .env.example .env
```

В .env заполните LLM_API_KEY и LLM_MODEL. API должен поддерживать Chat Completions
и JSON-ответы через response_format=json_object. По умолчанию URL — https://api.deepseek.com.
Укажите модель, доступную в вашем аккаунте. Ключ не нужно присылать в чат или коммитить.
Для другого совместимого API задайте LLM_BASE_URL (с /v1, если его требует провайдер).

```bash
npm run doctor
npm run index
npm start
```

В интерактивном терминале:

```text
/help Как устроена структура проекта?
/help Как загружаются данные?
/help Какая сейчас Git-ветка?
/help Сначала найди правила релиза, затем сопоставь их с файлами проекта.
/sync HEAD~1
/sync HEAD~1 --apply
/exit
```

Одноразовый запуск: `npm run ask -- /help Как устроен проект?`.
Диагностика без ключа и без LLM: `npm run ask -- --retrieve /help Как загружаются данные?`.
Она показывает только первичную лексическую выдачу и MCP, без агентного выбора и проверки полноты.
`npm test` проверяет интеграцию с настоящим MCP; вызовы платной модели подменены тестовым API.

## VPS: консольный запуск

Сначала перенесите в копию репозитория добавленные файлы. Нужны docs, tools/dev-assistant,
обновлённый README/.gitignore и workflow. Сохраните их коммитом перед использованием --apply.
Затем в tools/dev-assistant создайте .env и заполните настройки модели.

```bash
sudo docker compose build
sudo docker compose run --rm assistant src/cli.js --doctor
sudo docker compose run --rm assistant
```

Для повседневного запуска достаточно команды из корня репозитория:

```bash
./assistant
```

Появится приглашение `>`. В нём вводите /help или /sync; /exit завершает процесс.
Браузер, HTTP-сервер, SSH-туннель и открытые порты не используются.
Одноразовый запрос: `./assistant /help Какая сейчас Git-ветка?`.
Каждый запуск читает актуальный .env; после изменения ключа перезапуск отдельного сервиса не нужен.
Для отдельной копии приложения задайте PROJECT_PATH в .env (абсолютный путь на VPS).
Compose монтирует её в /project; PROJECT_ROOT нужен для запуска без Docker.
Репозиторий в контейнере подключён только для чтения. Для сохранения docs задайте
явный writable mount нужной копии приложения; пример для копии рядом с tools:

```bash
docker compose run --rm -v "$PWD/../..:/project" assistant src/cli.js /sync HEAD~1 --apply
```

Обновление копии проекта на VPS выполняется отдельно через git pull после сохранения локальных изменений.
После /exit одноразовый контейнер удаляется автоматически.

## Автоматические docs PR после влитых изменений

Workflow docs-sync.yml запускает тот же код агентов на GitHub runner, не на VPS.
После push в develop/main сравниваются github.event.before и HEAD: это охватывает весь push,
включая merge-коммиты и несколько коммитов. В docs-only PR workflow повторно не запускается.
Можно запустить вручную через Actions → Update documentation with AI → Run workflow,
задав base-коммит. Первый push новой ветки пропускается: у него нет предыдущего SHA.

В Settings → Secrets and variables → Actions настройте:

- Secret LLM_API_KEY.
- Variable LLM_MODEL.
- Необязательную variable LLM_BASE_URL.

В Settings → Actions → General разрешите GitHub Actions создавать pull requests.
Workflow создаёт/обновляет draft PR automation/docs-sync-<SHA> только с разрешёнными docs-файлами.
У каждого push отдельная ветка предложения: новый запуск не перезаписывает ожидающий PR прошлого push.
Автоматического слияния нет. В PR следует сверить изменение документации с исходным кодом.
Если генерация или проверка завершилась ошибкой, PR не создаётся.
